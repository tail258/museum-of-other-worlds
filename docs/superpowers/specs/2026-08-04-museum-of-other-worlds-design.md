# 异界遗物局 / Museum of Other Worlds — MVP 设计规格

## 1. 产品目标

用户上传一张现实物品照片，选择或输入一个自定义世界观，系统直接识别图片并生成一张原创、可下载、可公开分享的游戏式遗物档案卡。第一版以比赛现场稳定演示为最高优先级，不提供账号、支付、社交、AI 绘图、向量数据库、Agent 框架或独立 Python 后端。

## 2. 核心体验

1. 用户从首页进入创建页，或直接查看三个不调用模型的预置 Demo。
2. 用户选择本地世界观、创建新世界观并保存，或仅为本次填写世界观。
3. 用户选择黑暗幻想、复古科幻或废土档案主题。
4. 用户上传一张图片并看到本地预览。
5. 用户点击“开始鉴定”，服务端读取图片与世界观，返回结构化遗物资料。
6. 页面直接显示遗物卡。轻微误识别保留为“异文明误读”；严重失败时提示重新鉴定或载入 Demo。
7. 用户无需重新调用模型即可切换主题，可重新鉴定、导出 PNG，或主动发布为公开链接。

## 3. 技术架构

采用 Next.js App Router、React、TypeScript、Tailwind CSS 的全栈单体。一个代码仓库、一个部署单元，同时保持模型和存储厂商中立。

### 3.1 页面与接口

- `/`：产品入口、流程说明和三个预置 Demo。
- `/create`：世界观、主题、图片上传、生成、预览、导出与发布的一体化工作台。
- `/worlds`：浏览器本地世界观管理，最多保存 5 个。
- `/artifact/[id]`：从公开存储读取已发布作品并渲染只读分享页。
- `/api/identify`：校验输入，调用统一模型 Provider，校验输出并在失败时修复重试一次。
- `/api/artifacts`：压缩并发布源图与作品 JSON，返回公开作品 ID。
- `/api/artifacts/[id]`：读取公开作品 JSON。

### 3.2 模型适配

业务层只依赖 `AIProvider`：

```ts
interface AIProvider {
  identify(input: IdentifyInput): Promise<ArtifactAnalysis>;
}
```

首版提供：

- `OpenAICompatibleProvider`：使用标准 `fetch` 调用由环境变量指定的 OpenAI 风格接口，不引入具体厂商 SDK。
- `MockAIProvider`：根据 Demo 标识或输入特征稳定返回预置结果，无 Token 也可开发和演示。

环境变量：`AI_PROVIDER`、`AI_BASE_URL`、`AI_API_KEY`、`AI_VISION_MODEL`、`AI_TEXT_MODEL`。模型输出统一通过 Zod 校验。首次校验失败时，将错误路径和原始返回一并用于一次修复请求；第二次失败返回可操作错误，不继续重试。

### 3.3 数据结构

核心分析结构固定为：

```ts
type ArtifactAnalysis = {
  objectSummary: string;
  artifactName: string;
  description: string;
  appraiser: string;
  evidence: string;
  worldName: string;
};
```

客户端作品在此基础上增加 `id`、`theme`、`createdAt`、`worldPrompt` 和本地图片引用。三个视觉主题只消费同一结构，不拥有独立模型提示或数据字段。

### 3.4 本地世界观

使用 Dexie 管理 IndexedDB。世界观包含 `id`、`name`、`prompt`、`createdAt`、`updatedAt`。最多保存 5 个；达到上限时明确提示用户先删除一个，不自动覆盖。世界观数据不上传。

### 3.5 公开分享

存储层只依赖 `StorageProvider`，开发环境使用本地文件实现，生产环境使用通用 S3-compatible 实现。普通生成只存在浏览器；用户点击“发布分享”后才上传：

- `artifacts/{id}/source.webp`
- `artifacts/{id}/artifact.json`

公开 ID 使用不可预测的随机 ID。服务端限制图片类型与大小、重新编码图片，并只保存渲染分享页所需字段。分享页不执行用户输入的 HTML。

## 4. 视觉与交互设计

整体身份是“管理异文明遗物的跨界机构”，强调档案、鉴定、编号、封存和证据链，不采用聊天气泡或通用 AI 渐变界面。

创建页为双栏工作台：桌面端左侧是三步控制区，右侧是持续可见的遗物卡；移动端按控制区、结果卡、操作区顺序堆叠。首页 Hero 直接展示可切换主题的预置遗物卡，让用户先看到结果，再理解流程。

三套主题共享信息层级：世界名称、原始照片、遗物名称、说明、鉴定者、解释依据、档案编号。视觉表现分别为：

- 黑暗幻想：炭黑、旧银、褪金与暗紫；石刻边框、宗教印记、低饱和照片滤镜。
- 复古科幻：深靛、氧化青、警示橙与冷白；CRT 网格、技术标尺、模块化铭牌。
- 废土档案：尘灰、军绿、锈红与纸黄；磨损纸张、分类戳、手写批注感标记。

标志性动效为“鉴定扫描光栅”：鉴定完成时，一条窄光栅扫过照片并逐段显现档案信息。其他动效保持克制；系统设置为减少动态效果时取消扫描和平移动画。

所有纹理由 CSS、内联 SVG 或项目内自制 WebP/PNG 构成。字体优先合法 Web 字体或系统降级，不提交第三方字体文件。每个外部素材在 `THIRD_PARTY_ASSETS.md` 记录来源、作者、许可证和使用位置。

## 5. 错误处理

- 图片格式或大小不合规：在上传区说明允许格式、大小和修复方式。
- 模型不可用或结构化输出失败：保留用户输入和图片，允许重新鉴定，并提供载入 Demo 的按钮。
- IndexedDB 不可用：退化为本次会话可用，并说明世界观无法持久保存。
- PNG 导出失败：保持卡片可见，允许重试，不影响发布。
- 发布失败：本地作品不丢失，显示具体失败阶段并允许重试。
- 分享 ID 不存在：显示机构风格的“档案未收录”页面并返回正确的 404 状态。

## 6. 测试策略

- 单元测试：Zod Schema、模型响应解析与单次修复重试、世界观数量上限、主题与数据解耦、存储路径及发布载荷清洗。
- 组件测试：上传预览、创建表单、主题切换、生成错误状态、世界观管理。
- 端到端测试：Mock 模式下完成“选择 Demo/上传 → 鉴定 → 切换主题 → 导出入口 → 发布 → 打开分享页”的核心流程。
- 构建检查：TypeScript、ESLint、Vitest 和 Next.js production build。

## 7. 实施顺序

1. 建立 Next.js、测试环境、共享 Schema、Mock Provider 和单卡生成闭环。
2. 完成世界观 IndexedDB 管理和三个预置 Demo。
3. 完成三套视觉主题及响应式布局。
4. 完成 PNG 导出。
5. 完成本地与 S3-compatible 公开分享适配。
6. 完成扫描动效、错误状态、可访问性、素材许可和部署文档。

## 8. 验收标准

- Windows 11 按 README 可启动，未配置 Token 时默认 Mock 模式可完整演示。
- 三个 Demo 不调用外部模型。
- 真实 Provider 的业务调用不依赖任何模型厂商 SDK。
- 三套主题切换不产生新模型请求。
- 本地世界观最多保存 5 个，普通生成不上传任何内容。
- PNG 导出包含照片、主题视觉和完整遗物文字。
- 主动发布后能通过公开 URL 查看作品。
- 核心测试、类型检查、Lint 和生产构建通过。
- `.env.example`、README、Provider 接入、部署说明、素材许可清单和 Git 提交建议齐全。
